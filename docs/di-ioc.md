# DI и IoC-контейнер: зачем это нужно и как работает в NestJS

Примеры взяты из нашего проекта betting-platform. Открывай файлы рядом и сверяйся.

## Проблема

Посмотри на `BetsService`. Чтобы создать ставку, ему нужно:

- `BetsRepository`, чтобы сохранить ставку в базу
- `AccountsService`, чтобы найти счёт пользователя
- `AccountsTransactionsService`, чтобы списать деньги
- `OutcomesRepository`, чтобы проверить исход события

А у `BetsRepository` своя зависимость: подключение к базе. Подключению нужен конфиг. Конфигу нужен `.env`. Получается цепочка, и кто-то должен собрать её целиком.

## Наивный вариант: создаём всё сами

Самое очевидное решение: каждый класс сам создаёт то, что ему нужно.

```ts
class BetsService {
  private betsRepository = new BetsRepository();
  private accountsService = new AccountsService();

  createBet() {
    // ...
  }
}
```

Работает. Пока проект маленький. Потом начинаются неприятности:

1. `BetsRepository` теперь требует подключение к базе. Придётся поправить каждое место, где есть `new BetsRepository(...)`.
2. Подключений к базе станет столько, сколько раз ты написал `new`. База такого не любит.
3. Как протестировать `BetsService` без настоящей базы? Никак, репозиторий зашит внутри.
4. Хочешь заменить `EmailService` на другой? Ищи и правь все классы, которые его создают.

Корень проблемы: класс одновременно делает свою работу и решает, откуда брать помощников. Это две разные задачи.

## Шаг 1: пусть зависимости приходят снаружи

Уберём `new` из класса и попросим всё в конструкторе:

```ts
class BetsService {
  constructor(
    private betsRepository: BetsRepository,
    private accountsService: AccountsService,
  ) {}
}
```

Теперь `BetsService` не знает, как создаётся репозиторий. Ему дали, он пользуется. В тесте можно подсунуть фальшивый репозиторий, и база не нужна.

Это и есть **Dependency Injection** (внедрение зависимостей). Название страшное, идея простая: не создавай помощников сам, попроси их в конструкторе.

## Шаг 2: собираем всё вручную в одном месте

Кто-то всё равно должен вызвать `new`. Соберём всё в одном файле, например `main.ts`:

```ts
const config = new AppConfigService();
const knex = createKnex(config);

const betsRepository = new BetsRepository(knex);
const accountsRepository = new AccountsRepository(knex);
const accountsService = new AccountsService(accountsRepository);
const outcomesRepository = new OutcomesRepository(knex);
// ...
const betsService = new BetsService(betsRepository, accountsService, outcomesRepository);
```

Уже лучше: все связи в одном месте. Но у нас больше десятка сервисов и репозиториев. Порядок важен: нельзя создать `BetsService` раньше `AccountsService`. Добавил зависимость в конструктор? Иди в этот файл и поправь вручную. Файл разрастается, и в нём легко ошибиться.

Хочется, чтобы кто-то делал это за нас.

## Шаг 3: IoC-контейнер

**IoC** (Inversion of Control, инверсия управления) значит, что не твой код решает, когда и как создавать объекты. Этим занимается кто-то другой. **IoC-контейнер** это и есть этот «кто-то». Он делает три вещи:

1. Знает, какие классы существуют (регистрация).
2. Читает, что каждому классу нужно в конструкторе.
3. Сам создаёт объекты в правильном порядке и отдаёт их туда, где нужно.

Представь официанта. Ты не идёшь на кухню и не готовишь суп. Ты говоришь «мне суп», и приносят. Контейнер здесь официант: ты называешь, что тебе нужно, а как это приготовить, он разбирается сам.

## Как это работает в NestJS

В Nest контейнер уже встроен. От тебя нужны три вещи.

### 1. Пометить класс: `@Injectable()`

```ts
@Injectable()
export class BetsService {
  constructor(
    private readonly betsRepository: BetsRepository,
    private readonly accountsService: AccountsService,
  ) {}
}
```

Декоратор говорит контейнеру: «этот класс можно создавать и выдавать другим». Типы в конструкторе это и есть список желаний. TypeScript сохраняет их, и Nest по ним понимает, что класть в конструктор.

### 2. Зарегистрировать класс в модуле

Пометить класс мало. Контейнер должен узнать, что он существует. Регистрируем в `providers`:

```ts
@Module({
  providers: [BetsService, BetsRepository],
})
export class BetsModule {}
```

`provider` (поставщик) это просто класс, который контейнер умеет создавать.

### 3. Попросить в конструкторе

Больше ничего. Нигде в проекте нет `new BetsService()`. Nest при старте читает все модули, строит граф зависимостей и создаёт объекты по порядку: конфиг, потом подключение к базе, потом репозитории, потом сервисы, потом контроллеры.

По умолчанию каждый провайдер создаётся один раз, и все получают один и тот же экземпляр (singleton). Поэтому подключение к базе у нас одно на всё приложение.

## Модули: что видно снаружи

Допустим, `BetsService` просит `AccountsService`, а тот объявлен в `AccountsModule`. Nest не отдаст его просто так. Модуль должен явно выставить его наружу, а соседний модуль должен явно подключить его.

В `AccountsModule`:

```ts
exports: [AccountsService, AccountsRepository],
```

В `BetsModule`:

```ts
imports: [AccountsModule, /* ... */],
```

Это как с офисом: у каждой команды свой кабинет. Чтобы воспользоваться чужим инструментом, команда должна его выдать (`exports`), а ты должен прийти к ней (`imports`).

Есть исключение. `DatabaseModule`, `AppConfigModule` и `LoggerModule` помечены `@Global()`. Их содержимое доступно везде без `imports`, потому что нужно почти всем.

## Когда класса недостаточно: токены и фабрики

Подключение к базе (`Knex`) это не наш класс, а объект из библиотеки. Для него нет `@Injectable()`. Как его зарегистрировать? Смотри `database.module.ts`:

```ts
export const KNEX_CONNECTION = Symbol('KNEX_CONNECTION');

providers: [
  {
    provide: KNEX_CONNECTION,
    inject: [AppConfigService],
    useFactory: (config: AppConfigService) =>
      knex({ client: 'pg', connection: config.database }),
  },
],
```

Читается так: «Когда кто-то попросит `KNEX_CONNECTION`, вызови эту функцию, подставив ей `AppConfigService`, и отдай результат».

- `provide` это имя (токен), по которому будут просить.
- `inject` это то, что нужно фабрике для работы.
- `useFactory` это функция, которая создаёт объект.

А просят так, в `bets.repository.ts`:

```ts
constructor(@Inject(KNEX_CONNECTION) private readonly knex: Knex) {}
```

Для классов Nest использует сам класс как токен, поэтому `@Inject` там не нужен. Для всего остального токен приходится указывать руками.

## Типичные ошибки

Ошибка `Nest can't resolve dependencies of the BetsService (?, ...)` почти всегда означает одно из трёх:

1. Забыл добавить класс в `providers`.
2. Нужный класс живёт в другом модуле, и его не подключили через `imports`.
3. Другой модуль подключён, но не добавил класс в `exports`.

Знак вопроса в сообщении показывает позицию в конструкторе, на которой споткнулся контейнер. Считай параметры с нуля и сразу найдёшь виновника.

## Что запомнить

- Класс не создаёт помощников сам, а просит их в конструкторе. Это DI.
- Кто-то должен всё собрать. Вручную это быстро превращается в боль, поэтому сборку отдают контейнеру. Это IoC.
- В Nest: `@Injectable()` на класс, класс в `providers` модуля, остальное делает контейнер.
- Между модулями зависимости ходят через `exports` и `imports`.
- Для объектов не из твоего кода используй токен и `useFactory`.
