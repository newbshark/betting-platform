# Как писать DTO: восклицательный знак, вопросительный знак или ничего

DTO (Data Transfer Object) это класс, который описывает форму данных: что пришло в запросе или что мы отдаём в ответе. Никакой логики в нём нет, только поля.

Сейчас у нас так:

```ts
export class TransactionResponseDto {
  id!: number;
  type!: 'CREDIT' | 'DEBIT';
  amount!: string;
  balanceAfter!: string;
}
```

Предлагаю писать проще:

```ts
export class TransactionResponseDto {
  id: number;
  type: 'CREDIT' | 'DEBIT';
  amount: string;
  balanceAfter: string;
  description?: string;
}
```

Правило такое: обязательное поле пишем как `amount`, необязательное как `description?`. Восклицательный знак не нужен.

## Что вообще означают эти знаки

Знак `?` после имени говорит: поля может не быть. Тип становится `string | undefined`, и каждый, кто берёт это поле, обязан учесть пустоту:

```ts
dto.description.toUpperCase();      // ошибка компиляции
dto.description?.toUpperCase();     // ок
```

Знак `!` (по-английски definite assignment assertion) говорит компилятору: «поле точно получит значение, не проверяй». Тип при этом не меняется, `amount!: string` остаётся обычным `string`. Влияет `!` на одну-единственную проверку, о ней ниже.

Так что `!` не делает поле обязательным и не защищает от `undefined`. Он затыкает компилятор.

## Зачем люди ставят `!`

Без него TypeScript иногда ругается:

```
Property 'amount' has no initializer and is not definitely assigned in the constructor. (TS2564)
```

Эта ошибка появляется, когда включена опция `strictPropertyInitialization` (она входит в общий флаг `strict`). Она требует, чтобы каждое поле класса получило значение сразу или в конструкторе. У DTO конструктора нет, значения приходят извне, поэтому в строгом режиме без `!` поля краснеют. Отсюда и привычка лепить `!` везде: так быстрее всего заставить ошибку замолчать.

## Что у нас в tsconfig

Смотрим `tsconfig.json` проекта. Там включено только `strictNullChecks`. Общего `strict` нет, `strictPropertyInitialization` нет. Значит, прямо сейчас этой ошибки не будет, и запись без `!` скомпилируется. Можешь проверить сам: убери `!` из любого DTO и запусти `pnpm run build`.

Отсюда две вещи. Во-первых, сегодня `!` у нас ничего не делает. Это шум, и он сбивает с толку: кажется, что тут происходит что-то важное. Во-вторых, если когда-нибудь включим `strict`, ошибки полезут сразу во всех DTO.

## Главный совет: чини tsconfig, а не каждое поле

Если ошибка мешает, не нужно ставить `!` на каждое поле каждого DTO. Достаточно один раз сказать компилятору, что эта проверка нам не нужна. В `tsconfig.json`:

```json
"strict": true,
"strictPropertyInitialization": false
```

Остальная строгость остаётся, а DTO пишутся без знаков. Одна строка в конфиге заменяет сотню восклицательных знаков в коде. Для Nest-проекта с кучей DTO это самый чистый вариант.

Если конфиг по какой-то причине менять нельзя, `!` остаётся рабочим запасным вариантом. Просто помни, что он ничего не гарантирует, а лишь заглушает ошибку.

Есть и третий путь: не использовать классы там, где они не нужны. Ответы, которые мы сами собираем в сервисе, можно описать через `interface` или `type`. У них нет «инициализации», так что и ошибки не будет:

```ts
export interface TransactionResponse {
  id: number;
  type: 'CREDIT' | 'DEBIT';
  amount: string;
  balanceAfter?: string;
}
```

Но для входящих DTO (`CreateBetDto` и подобных) класс нужен: `ValidationPipe` и `class-validator` работают с декораторами, а их можно повесить только на класс.

## Что на самом деле защищает от пустых значений

Ни `amount`, ни `amount!` не гарантируют, что значение придёт. Типы TypeScript живут только до компиляции, в готовом JavaScript их нет. Что реально прилетит в запросе, компилятор не знает.

Для входящих данных это проверяют валидаторы:

```ts
export class CreateBetDto {
  @IsInt()
  @IsPositive()
  userId: number;
}
```

Если клиент пришлёт без `userId`, `ValidationPipe` вернёт 400 до того, как код дойдёт до сервиса. Именно декоратор защищает от пустоты, а не восклицательный знак.

Для ответов защита другая: мы сами формируем объект в сервисе (как `toResponse` в `BetsService`), и если забыть поле, ошибку покажет компилятор, потому что объект не подойдёт под тип.

## Итого

- Обязательное поле: `amount: string`.
- Необязательное: `description?: string`.
- `!` не делает поле обязательным и не спасает от `undefined`. Он нужен только в строгом режиме, чтобы заглушить TS2564.
- В нашем `tsconfig` эта проверка выключена, поэтому `!` сейчас лишний.
- Если строгий режим включат, правим `tsconfig` (`strictPropertyInitialization: false`), а не каждое поле.
- От пустых значений в запросах защищает `class-validator`, а не типы.

## Попробуй сам

1. Убери `!` из `account-operation-response.dto.ts` и собери проект. Убедись, что ошибок нет.
2. Добавь в `tsconfig.json` `"strictPropertyInitialization": true` и пересобери. Посмотри на сообщения. Потом верни как было.
3. Сделай поле `description?` в ответе и попробуй вызвать на нём `.length` без проверки. Что скажет компилятор?
